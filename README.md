# 契衡 · 合同审批审查系统

面向企业合同审批场景的智能审查系统。支持 **DOCX / PDF / 图片扫描件** 合同解析与条款层级切分，结合
**规则引擎 + 大模型语义审查**识别法律合规与商业风险，提供原文高亮定位、智能修改建议与报告导出，
并可将审查意见**自动回写**至企业审批系统评论区（演示环境为内存模拟）。

> 产品名：**契衡（QiHeng）** —— 以规则为衡，审每一份契约。
>
> 对应《项目实战》文档 **第 2.4 节「合同审批审查系统」** 要求实现。

## 一、功能对照（验收标准 2.4.10）

| 验收项 | 实现情况 |
|--------|----------|
| 解析 DOCX / PDF / 图片扫描件 | ✅ `services/doc_parser.py`，图片走可插拔 OCR 适配层 |
| 提取核心元数据与条款，记录页码与位置 | ✅ 主体/信用代码/金额/期限/生效条件 + 条款类别切分，含字符偏移 |
| 必备条款缺失/权责不对等/高危表述合规审查，输出风险等级与依据 | ✅ `services/rule_engine.py` + `llm_review.py` |
| 工作台原文与风险卡片双向高亮定位 | ✅ 前端双栏联动（点击卡片跳正文、点击高亮跳卡片） |
| 针对风险条款生成可落地修改示范条款并支持法务编辑 | ✅ `services/clause_recommend.py` + 前端批注/复制 |
| 格式化审查意见写回审批系统评论区 | ✅ `services/approval_writeback.py`（模拟回写） |
| 解析失败进入阻塞状态并支持重试 | ✅ 状态机 `blocked` + 前端「重试」 |
| 至少完成一个典型合同端到端演示 | ✅ 内置两份示例合同（采购/销售） |
| 合规规则与模板可视化维护 | ✅ 「合规规则与模板」页：三标签页 + 顶部筛选条（含风险分级速筛）+ 卡片网格 + 卡内启停 + 新增示范条款 |
| 拍照识别纸质合同（图片 → 正文 → 审查） | ✅ `services/ocr_service.py`：四引擎可插拔 + 图片体检 + 人工校对 + 明确降级 |
| 多张照片按页识别（一页一张，最多 20 页） | ✅ 逐页识别/校对/调序/重拍，**页码严格等于照片序号**（空页保留页次） |
| 登录（三角色）与退出二次确认 | ✅ 会话守卫 + 角色权限矩阵；退出走确认弹窗（显示待退出身份，取消/遮罩/`Esc` 三条放弃路径） |
| 失败审查任务外发钉钉（条件筛 + 人工确认） | ✅ 「失败外发审核」页：可配条件门禁（逐条可解释）+ 待审队列 + 确认/驳回/重试 + 全程留痕 |

## 三、环境搭建与启动

> 已随项目生成隔离虚拟环境所需依赖；以下命令在 **Windows PowerShell / Git Bash** 中执行。

```bash
# 1. 创建并激活隔离 venv（如使用本机其他 Python 亦可）
python -m venv .venv
.venv\Scripts\activate        # Windows
#   source .venv/bin/activate # Linux/Mac

# 2. 安装依赖
pip install -r requirements.txt

# 3. （可选）如需拍照/图片自动识别，再装：
# pip install Pillow numpy        # 图片体检（分辨率/清晰度/亮度/对比度）
# pip install pytesseract         # 本地离线 OCR 的 Python 包
# 不装也可正常使用：识别引擎不可用时，弹窗会说明原因并引导人工录入正文

# 3.1 只装 Python 包还不够，还要装 Tesseract-OCR 程序（Windows）：
# winget install UB-Mannheim.TesseractOCR --accept-package-agreements --accept-source-agreements
#
# 3.2 安装程序默认**不带中文语言包**，必须补装 chi_sim，且有个坑：
#     引擎装在 C:\Program Files\Tesseract-OCR\，其 tessdata 目录**不可写**，语言包补不进去。
#     解决办法是建一个用户级目录并把语言包放进去，服务会自动优先使用它：
#       mkdir %USERPROFILE%\.workbuddy\tools\tesseract\tessdata
#       copy "C:\Program Files\Tesseract-OCR\tessdata\eng.traineddata" ^
#            %USERPROFILE%\.workbuddy\tools\tesseract\tessdata\
#       下载 chi_sim.traineddata 放进同一目录（~2.4MB）：
#       https://github.com/tesseract-ocr/tessdata_fast/raw/main/chi_sim.traineddata
#     也可在 config.py 里用 TESSERACT_CMD / TESSDATA_DIR 显式指定程序与语言包路径。

# 4. 生成示例合同（首次运行或想刷新样例时）
python data/samples/generate_samples.py

# 5. 启动服务
python main.py
# 或： uvicorn main:app --host 127.0.0.1 --port 18090
```

启动后访问： **http://127.0.0.1:18090** → 自动跳转登录页 **/login**。

## 四、演示步骤（端到端）

0. 打开 **http://127.0.0.1:18090/login**，点击演示账号行一键填充后登录（建议先用 **法务合规经理** `zhoumingyuan@gmail.com / zhoumingyuan`）。
1. 进入「审查大盘」（顶部为 **合同总数 / 待审任务 / 高风险合同 / 本周审结** 概览卡），点击 **＋ 上传合同并审查**，选择 `data/samples/` 下任意一份示例合同
   （如 `大额销售合同_违约责任不对等.pdf`），在弹窗中从**下拉框选择业务类型**（采购/销售/服务/劳动/租赁/技术/未分类），点「确定并审查」
   （点「取消」或按 Esc 则放弃本次上传）。
2. **（另一种入口）点击 📷 拍照识别合同**：手机端会直接调起后置摄像头，桌面端选图 → **支持多张照片（一页一张，最多 20 页）**，
   也支持把照片直接拖进弹窗。弹窗先展示本机**引擎能力**，逐页给出**图片体检**（分辨率/清晰度/亮度/对比度 + 重拍建议）、
   **识别过程**（各引擎为什么没识别出来的逐条说明）与**可编辑的逐页正文**；每页可**上移/下移/重拍/删除**，
   人工校对错字后点「提交审查」，走的是与上传文档**完全相同**的闸门 → 规则 → 语义审查链路。
   > **留空页不参与审查，但会保留页次**：纸质合同常有空白页/封面页，强行要求填写等于逼用户编内容；
   > 但也不能把空页丢掉——否则后面几页的页码会整体前移，你照着报告里的「第 3 页」去翻自己拍的第 3 张照片就会对不上。
   > 系统保证 **「第 N 页」始终等于「第 N 张照片」**。
   >
   > 本机未安装任何 OCR 引擎时，弹窗会明确写出「未安装可用的 OCR 引擎（Tesseract / 多模态大模型 / 云 OCR 均不可用）」及安装指引，
   > 并引导你对照照片逐页人工录入正文——**不会卡在"解析受阻"上无从下手**。
3. 系统自动完成 **解析 → 文档类型校验 → 规则审查 → 大模型语义审查 → 条款推荐 → 报告装配**，状态变为「审查完成」。
4. 点击「进入工作台」：
   - **左栏**展示合同正文，风险条款已按等级高亮；
   - **右栏**按高/中/低列出风险卡片（含成因、法律依据、AI 建议修改条款）；
   - 点击风险卡片 → 左栏自动滚动并闪烁对应原文；点击原文高亮 → 右栏定位对应卡片（**双向联动**）。
5. 在「审批协同与回写」区填写法务批注，点击 **一键回写审批单**，状态变为「回写成功」。
6. 点击 **导出 Markdown** 下载审查意见；或 **打印 / 导出 PDF** 生成正式文书。
7. 切到顶部「**合规规则与模板**」：三个规则标签页各是一页**卡片网格**，一条规则一张卡；
   上方筛选条可按维度 / 业务类型点选、也可用右侧三个胶囊只看某个风险等级，还能直接搜索，
   筛选生效时右侧显示「筛出 N / 总数」并提供一键清空；点卡片展开查看判定依据。
   **切换卡片上的「启用」开关后回到大盘重新审查同一份合同**，可观察到对应维度的风险发现随即消失
   （例如关掉「保密义务缺少期限」后，保密维度不再报警）——这就是"规则变更即时生效"。
8. 切到顶部「**失败外发审核**」，演示**失败任务的钉钉告警闭环**：
   1. 页头右侧点「**通道测试**」可验证钉钉通道，结果在条件卡下方提示条给出
      （未配 Webhook 时为模拟模式，消息不会真正发出，仅留痕）；
   2. 回大盘传一个**坏文件**（任何非 PDF/DOCX 的二进制改名成 `.pdf` 即可）→ 状态变「解析受阻」，
      失败任务**自动进入待审队列**（系统默认只纳入「解析受阻」这一类——「非合同被拒」是闸门的正常工作结果，
      用户传错文件不该刷屏钉钉群）；
   3. 展开待审卡片，能看到**逐条条件的期望值与实际值**（哪几项命中、哪几项不限而跳过），
      以及**入队时已冻结的消息正文预览**——审核人预览到的就是实际会发出的内容；
   4. 填审核意见后点「确认推送」→ 模拟模式下记录为「已推送」，配了 Webhook 则真发到钉钉群；
   5. 试试点「驳回」不填理由——会被挡下（**驳回必须留痕**，否则队列被无声清空后无从回溯"为何该失败未外发"）；
   6. 改条件（例如把「非合同被拒」也纳入）→ 点「扫描」补扫历史任务，可看到原先被拦下的任务补入队列；
      被拦下的记录同样留痕，并写明是**哪个条件没过**。

> 演示用示例：
> - `软件采购合同_知识产权与付款风险` —— 命中「违约责任不对等」「付款前置验收缺失」「保密期限缺失」；
> - `大额销售合同_违约责任不对等` —— 命中「违约责任不对等」「管辖地约定不合规」「违约金比例超限」「付款前置验收缺失」等。

## 四·附、合规规则与模板页（规则库配置台）

面向法务/管理员的规则维护入口，采用**三标签页 + 顶部筛选条 + 卡片网格**的结构：
一条规则（或一条条款 / 一项核验）就是一张卡，卡片**左侧的色条**直接反映风险等级，
编号 / 等级 / 启用开关收在卡头一行，规则名独立成标题，元信息退为次要行。

| 标签页 | 每张卡片承载的信息 | 数据来源 |
|--------|------|----------|
| 审查规则库（13） | 规则编号 · 风险分级（左侧色条 + 胶囊） · 启用开关 ／ 规则名称 ／ 审查维度 · 适用范围 · 匹配方式 | `data/rules/review_rules.yaml` |
| 标准示范条款库（8） | 条款键 · 关联维度 · 复制正文 ／ 条款名称 ／ 正文摘要（两行截断） · 引用规则 | `data/rules/clause_library.yaml` |
| 主体资质库（5） | 核验编号 · 风险分级 ／ 核验项名称 ／ 审查维度 · 数据来源 · 状态 | `data/rules/party_qualification.yaml` |

**页面能力**

- **顶部筛选条**：维度与业务类型两组 pill 横向铺在顶部（**按命中数降序**，规则最多的维度自动排最前），点选即筛；
  右侧实时显示「筛出 N / 总数」，有任一条件生效时才出现「✕ 清空筛选」一键复位。
  业务类型按 scope 统计各类型**专属**规则数——点「采购」为空即表示该类合同暂无针对性规则，系统仍会执行全部「全部类型」规则。
- **风险分级速筛**：规则页额外提供 高风险 / 中风险 / 低风险 三个胶囊（各带条数），点一下只看该等级，再点取消。
- **搜索**：支持按名称、编号、维度、匹配方式模糊过滤。
- **卡片展开**：点击卡片任意位置，在卡内展开风险成因、合规依据、判定方式说明、关联示范条款。
- **启用开关**：直接切换规则的 `enabled`，**写回 YAML 并即时重载规则引擎**——无需重启服务，后续审查任务立刻按新开关执行；改开关只改动目标规则那一处（`true`/`false` 各 1 字符），文件注释、字段顺序与换行风格均原样保留。
- **新增示范条款**：弹窗填写名称 / 关联维度 / 正文，原子追加写入 `clause_library.yaml` 并重载条款库，新条款即可被同维度风险的建议引用。

> 本页在 `#rules` 作用域内**局部覆盖**了一套颜色变量（主色用与顶栏一致的深蓝、风险三色与「审查大盘」同源），
> 因此规则页不会带着通用组件库的亮蓝观感；覆盖只在本页生效，拍照识别弹窗等模块不受影响。

**相关接口**

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/rules/config` | 规则库配置页全量数据（三个标签页 + 分面统计 + 计数） |
| POST | `/api/rules/{rule_id}/toggle` | 切换单条规则启用开关，`{"enabled": true|false}` |
| POST | `/api/rules/clauses` | 新增标准示范条款，`{"title","category","text","key"?}` |

> 权限：`biz`（采购业务经办）不可见本页；`admin` / `legal` 可查看与维护。

## 四·附二、拍照 / 图片识别（纸质合同入口）

纸质合同没法直接上传，`services/ocr_service.py` 提供「拍照 → 正文 → 审查」这条通道。

**四个引擎，按优先级自动尝试（可插拔）**

| 优先级 | 引擎 | 适用场景 | 启用条件 |
|--------|------|----------|----------|
| 10 | Tesseract 本地 OCR | 内网部署、数据不出域 | `pip install pytesseract` + 安装 Tesseract-OCR 程序（勾选 `chi_sim` 中文包） |
| 20 | 多模态大模型识图 | 手写、盖章、复杂版面 | `config.LLM_PROVIDER="openai"` 且模型支持图片输入 |
| 30 | 云 OCR 接口 | 有商用 OCR 服务时 | 配置 `OCR_API_URL` / `OCR_API_KEY` |
| 999 | 人工录入（兜底） | 前三个都不可用 | 始终可用 |

新增引擎只需继承 `OCRProvider` 并声明 `provider_name` / `priority`，`__init_subclass__` 会自动登记，
调用方无需改动——与 `core/node_base.py` 同一套注册约定。

**三个刻意的设计取舍**

1. **引擎缺失是可解释的降级事件，不是静默失败。** 旧实现在引擎缺失时返回空文本，用户只看到一句
   「解析受阻」，既不知道原因也不知道下一步；现在 `probe()` 会汇报每个引擎的可用性与修复指引，
   `recognize()` 返回的 `attempts` 逐条说明"为什么没试 / 试了为什么没出来"。
2. **体检在识别之前。** 分辨率、清晰度（拉普拉斯方差）、亮度、对比度先算出来，把"要不要重拍"提前告诉用户，
   而不是等识别失败才回头怀疑照片。
   > 过曝判定特意用「亮部占比高 **且** 对比度低于 20」而不是亮度均值：白纸黑字的合同照片白底占大半版面，
   > 均值天然在 245 以上，只看均值或只看亮部占比都会把正常照片误报为过曝（实测正常照片亮部占比就有 94%）。
3. **识别结果必须可编辑。** OCR 必然有错字，让法务在提交前就改掉，比审查完再回头改更省事，
   也避免错字触发规则误报。

**识别准确率：三条实测结论**

这几条都是在同一台机器上、用同一张合成合同图反复试出来的，改参数前请先读，别凭直觉调回去：

| 结论 | 实测依据 | 反面教训 |
|------|----------|----------|
| 语言包**只用** `chi_sim`，不加 `+eng` | `chi_sim+eng` 稳定把「甲方」认成 FA / FAA；纯 `chi_sim` 中文 6/6，**英文同样 6/6**（`PURCHASE CONTRACT`、`USD 1,200,000`、`Beijing ... Co., Ltd.` 全中，只丢了个句点） | 直觉上"中英文都认得更好"，实际中文被英文模型抢答；甲乙方是元数据与规则判定的基石字段，认错会直接产出「缺失甲方」的高风险假阳性 |
| 放大倍数**上限 1.5x**，不是越大越好 | 1500×472 的图按"短边补到 1200"放大 2.54x 后，「乙方」→ OH、「支付全款」→ ANTS.；不放大或 1.5x 反而 8/8 | Tesseract 对字符高度敏感，过度放大的插值失真会抵消分辨率收益 |
| 页面分割用 `psm 6`，配 `psm 3` 回退 | 三档分辨率共 24 个关键片段：psm 6 → 24/24，psm 3（默认）→ 22/24，psm 11 → 20/24，psm 12 → 19/24 | psm 6 假设"整图一个文本块"，遇表格/多栏会漏，所以保留 psm 3 回退 |

另外：**纯英文文档**走纯中文包会退化，所以当识别结果的汉字数少于 20 时会自动补跑一次 `chi_sim+eng` 并择优。

**拍照来源的风险告警会标明不确定性**

`RULE-ENT-001` 这类规则靠元数据判定，但「OCR 没认出甲方」与「合同真没写甲方」在规则上表现完全一样，
结论却天差地别。所以拍照识别提交的正文（`ReviewTask.source == "scan"`）在命中"字段缺失"类告警时，
原因末尾会附一段说明：

> 【识别来源提示】本文正文来自拍照识别，字段抽取可能受识别准确率影响；
> 请先对照照片确认该字段是「合同确实未写明」，还是「识别未认出」，再作判定。

上传电子文档的路径不带这段提示（文本层可信），避免把确定性告警说得含糊。

**多张照片 = 多页合同**

一份纸质合同往往有好几页，所以拍照入口是按「多页」设计的，而不是一次只收一张：

- 弹窗内**一页一张卡片**：有缩略图、有独立体检、有独立校对框，可**上移/下移/重拍/删除**。
  第 3 页拍糊了只需重拍第 3 页，不用整份重来。
- 页数上限由服务端下发（`config.MAX_SCAN_PAGES`，默认 20），前端不自行写死，
  避免前后端各有一个数、改一处漏一处。
- **空页不参与审查但保留页次**：`pages` 数组里留空的那一项不会被丢掉，而是保留它占的分页位。
  这样「第 N 页」严格等于「第 N 张照片」——去看风险卡片写的页码时，翻到的就是你拍的那一张。
- 提交时传的是**逐页正文数组** `pages`，而不是前端拼好的长字符串：页间分隔符（`PAGE_SEPARATOR`）
  决定了后端能否还原真实页码，这个约定只允许有一处定义（`services/ocr_service.py`），
  `services/doc_parser.py` 直接复用同一常量，前端不参与拼接。
- 页码归属由解析器的 `page_of()` **按分页符精确定位**，而不是按字符长度估算：
  估算在"某页特别长/特别短"时会指错页，对拍照件这种长短极不均匀的场景尤其不准。

**相关接口**

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/ocr/probe` | 探测本机各引擎可用性、修复指引、支持的图片格式与页数上限 |
| POST | `/api/ocr/recognize` | 上传图片 → 返回**逐页**识别结果（页数、每页体检、每页尝试链路、合并正文）；支持 `file` 表单字段重复 1~N 次实现多张一次提交 |
| POST | `/api/ocr/submit` | 提交校对后的正文，建任务并立即审查。多页传 `{"pages": ["第1页正文", "", "第3页正文"], ...}`（留空项保留页次）；单页仍兼容旧的 `{"text": "..."}` |

> 提交接口刻意走「写成 `.txt` 再交给解析器」，而不是新写一条审查入口——
> 这样拍照识别与上传文档共享同一套闸门、规则引擎与报告装配，不会因为多一个入口就出现两套行为不一致的审查逻辑。
> 同理，识别出的是非合同内容（如随手拍的通知）也会被文档闸门正常拦下。

## 四·附三、失败外发审核（钉钉）

审查失败的任务不该悄悄躺在系统里。这一页把它们按条件筛一道，交给责任人确认后推到钉钉群。

**链路**：审查失败 →（条件门禁筛噪）→ 待人工审核 →（责任人确认）→ 推送钉钉 → 留痕。

> 为什么中间必须有"人工确认"这一态：外发钉钉是**对外动作，发出去收不回来**。
> 条件只能筛掉噪音，替代不了责任人点头。

**双条件策略**（这是本功能的核心取舍）

| 关卡 | 作用 | 在哪配 |
|------|------|--------|
| 条件门禁 | 先筛掉**不值得打扰**的失败 | 页面「外发触发条件」卡，改完即时生效 |
| 人工确认 | 拦下"筛不掉但可能不该发"的 | 待审卡片上的「确认推送 / 驳回」 |

**可配的条件**（每项都可留空 = 不限）

| 条件 | 说明 |
|------|------|
| 失败类型 | `解析受阻`（文档没解析出正文，审查未走完）/ `非合同被拒`（闸门判定非合同）。**默认只纳入前者**——后者是闸门的正常工作结果（用户传错文件），不该刷屏钉钉群 |
| 已重试次数下限 | 例如设 1 表示"先让系统自己重试一次，还失败才通知" |
| 文件后缀白名单 | 如只关心 `.pdf, .docx` |
| 正文来源 | 上传电子文档 / 拍照识别 |
| 失败原因关键词 | 如只关心 `加密`、`扫描件` 导致的失败 |
| 自动去重 | 同一任务已推送过就不再重复入队 |

**关键设计**

- **判定必须可解释**：每条记录都列出**逐条条件的期望值与实际值**（`✓ 属于 解析受阻` / `· 重试次数 不限` / `✗ 文件类型`），
  而不是只给一个"通过/不通过"。被拦下的也留痕，说明**是哪个条件没过**——否则"为什么这条没通知我"就查不到。
- **消息正文在入队那一刻冻结**，审核人预览的就是实际会发出的内容。改条件只影响后续扫描，不会追溯改写已入队记录。
- **任务重新审查成功后，旧待审记录自动作废**（`superseded`）。否则重试已恢复的任务，过期失败提醒还可能被人一点发进群。
- **驳回必须填理由**，写入留痕——队列被人清空后仍能回溯"为何该失败未外发"。
- **通道测试可随时验证**：页头「通道测试」按钮即时探测钉钉通道，结果经条件卡提示条反馈
  （未配 Webhook 时走模拟通道，消息不会真正发出）。推送凭据一律脱敏展示（`access_token` 只显示首尾）。
- **失败也归因清楚**：钉钉业务错误码（`310000` 关键词不匹配、`300001` 签名/机器人失效等）、响应不是 JSON（被网关拦）、
  网络不可达，四类都给出各自的可操作提示，而不是笼统一句"推送失败"。

**相关接口**

| 方法 | 路径 | 说明 |
|------|------|------|
| GET | `/api/export/config` | 通道状态（是否配置、模式、脱敏凭据、告警）+ 当前条件与可选值 |
| POST | `/api/export/condition` | 更新条件（服务端做规范化：分隔符兼容、非法值丢弃） |
| GET | `/api/export/queue` | 记录列表（可按状态过滤）+ 统计 + 最近审计日志 |
| POST | `/api/export/scan` | 按当前条件扫描全部失败任务并入队（幂等，可反复点） |
| POST | `/api/export/{id}/approve` | 审核通过并推送（`{operator, note}`） |
| POST | `/api/export/{id}/reject` | 驳回（`note` 必填） |
| POST | `/api/export/{id}/retry` | 推送失败后重试（沿用审核时冻结的正文） |
| POST | `/api/export/test` | 发一条通道测试消息 |

> 审查流程在产生失败态（`blocked`）时会**自动触发门禁入队**，通常不必手点「扫描」；
> 「扫描」按钮用于条件改动后补扫历史任务，以及演示。

## 五、配置说明（config.py）

| 配置项 | 说明 |
|--------|------|
| `PORT` | 服务端口，默认 `18090`。**支持环境变量覆盖**：检测到 `PORT` 时自动绑 `0.0.0.0:$PORT`（托管环境），无该变量时仍是 `127.0.0.1:18090`（本地） |
| `HOST` | 监听地址，默认按上面规则推导；也可显式设环境变量 `HOST` 完全覆盖 |
| `MAX_UPLOAD_BYTES` | 单文件大小上限，默认 20MB（图片与文档共用；多张照片按张分别校验） |
| `MAX_SCAN_PAGES` | 拍照识别的**页数上限**，默认 20。由 `/api/ocr/probe` 下发给前端，前后端不各写一个数 |
| `OCR_API_URL` / `OCR_API_KEY` | 云 OCR 接口地址与密钥；留空则该引擎不参与尝试 |
| `TESSERACT_CMD` | Tesseract 可执行程序路径。留空时按 PATH → 常见安装目录自动探测（Windows 安装包**不会**刷新已运行进程的 PATH，所以探测是必需的） |
| `TESSDATA_DIR` | 语言包目录。留空时优先用 `%USERPROFILE%\.workbuddy\tools\tesseract\tessdata`（引擎装在 Program Files 时 tessdata 不可写，中文包只能放这里） |
| `LLM_PROVIDER` | `mock`（离线，默认，无需密钥）/ `openai`（真实大模型。设为 openai 后"多模态大模型识图"引擎同时可用） |
| `LLM_API_KEY` / `LLM_BASE_URL` / `LLM_MODEL` | 切换真实 LLM 时填写 |
| `APPROVAL_API_BASE` | 真实审批系统评论接口地址；留空则使用内存模拟回写 |
| `DINGTALK_WEBHOOK` | 钉钉群「自定义机器人」Webhook 地址。**留空即模拟模式**（记录为已推送但不真正发出，页面上有明确标注）。支持环境变量注入，便于部署时配密钥 |
| `DINGTALK_SECRET` | 机器人「加签」密钥（安全设置选"加签"时填）。服务端按钉钉规则算 `timestamp + HMAC-SHA256` 并 urlencode 拼接 |
| `DINGTALK_KEYWORD` | 机器人「自定义关键词」安全设置的关键词，默认 `合同审查`。**消息正文会带上它**，否则钉钉直接拒收 |
| `DINGTALK_AT_MOBILES` | 需要 `@` 的手机号（元组，可留空） |
| `EXPORT_ON_RUN` | 审查失败时是否自动触发门禁入队，默认 `True` |
| `EXPORT_CONDITION` | 外发触发条件（运行时可改，改内存即生效；重启回到 `DEFAULT_EXPORT_CONDITION` 出厂默认） |
| `MAX_EXPORT_RECORDS` | 外发记录保留条数上限（内存态，防长期运行无限增长） |

> **钉钉准备**：群设置 → 智能群助手 → 添加机器人 → 自定义（Webhook）。
> 安全设置三选一即可（推荐**加签**，最省事的是不设限制，但**不建议**）。
> 拿到 Webhook 后填 `DINGTALK_WEBHOOK`；选了加签再填 `DINGTALK_SECRET`。

> 图片是否走 OCR **不由开关决定**，而由各引擎的可用性探测决定（`ocr_service.probe()`）：
> 任一引擎可用就自动用它，全不可用则降级到人工录入。这样避免了"开关打开但引擎没装"这种自相矛盾的状态。

## 五·附、真实接入配置（LLM 直连与审批回写）

默认是 `mock` / 内存模拟，开箱即跑、零密钥。要接真实环境只需补配置项，无需改代码。
完整变量清单见仓库根目录 `.env.example`，下面是两类最常用的真实接入。

### 1）真实大模型（LLM 直连）

`services/llm_review.py` 用 `requests` **直连 OpenAI 兼容的 `/chat/completions` 接口**，
不依赖 `openai` SDK，因此 DeepSeek、本地 Ollama、各类企业网关都能直接填 `LLM_BASE_URL` 用。
未配置 `LLM_API_KEY` / `LLM_BASE_URL` 时**自动降级回 mock**，不会让整次审查因 LLM 未就绪而失败。

| 配置项 | 说明 |
|--------|------|
| `LLM_PROVIDER` | 设为 `openai`（真实）/ `mock`（离线，默认） |
| `LLM_BASE_URL` | 兼容接口的 base，如 `https://api.deepseek.com/v1` |
| `LLM_API_KEY` | 接口密钥 |
| `LLM_MODEL` | 模型名，如 `deepseek-chat` / `gpt-4o-mini` |
| `LLM_TIMEOUT` | 单请求超时（秒），默认 30 |
| `LLM_TEMPERATURE` | 生成温度，默认 0.1（审查求稳定可复现） |

容错策略：JSON 解析失败会先剥离 ```json 代码围栏再解析；接口超时/不可达最多重试；
**任何异常都降级 mock 并记日志**，保证审查流程不中断。

### 2）真实审批系统回写（HTTP）

`services/approval_writeback.py` 把审查意见 POST 到审批系统的评论接口；
未配置 `APPROVAL_API_BASE` 时走内存模拟回写（页面明确标注「模拟」）。

| 配置项 | 说明 |
|--------|------|
| `APPROVAL_API_BASE` | 审批系统 base，如 `https://oa.xxx.com` |
| `APPROVAL_API_TOKEN` | 鉴权令牌（可选） |
| `APPROVAL_AUTH_SCHEME` | `bearer`（默认，走 `Authorization`）/ `token-header`（走自定义头）/ `none` |
| `APPROVAL_AUTH_HEADER` | scheme=token-header 时用的请求头名，默认 `X-Approval-Token` |
| `APPROVAL_COMMENT_PATH` | 评论接口路径，拼在 base 后，默认 `api/approval/comment` |
| `APPROVAL_INSTANCE_FIELD` | 请求体里标记「审批单/实例」的字段名，默认 `instance_id` |
| `APPROVAL_TIMEOUT` / `APPROVAL_MAX_RETRIES` | 超时与重试次数 |

- **管理员可在线配置**：在「合规规则与模板」页填审批对接参数，等价于 `POST /api/approval/channel`，

- 回写评论正文含「合同基本信息 + 综合风险结论 + 风险清单（含页码/段落定位与法律依据）+ 法务批注」，

### 3）端到端演示（命令行）

## 六·附二、发布为在线应用（分享给别人看）

本机服务默认只监听 `127.0.0.1`，外部访问不到。要分享有两条路：

### 方式一：公网链接（推荐）

用「发布为应用」把项目发布成一个 HTTPS 链接，对方在任何网络、任何设备都能打开。

发布前**必须做两件事**：

1. **清掉测试残留。** `data/uploads/` 会积累历次演示上传的合同文件（本项目实测 125 MB，
   其中三个 38 MB 的 docx 是压测产物），它们会一起被打包上传，拖慢发布，
   还会让对方一进来就看到一堆历史任务。移走即可，不影响功能。
2. **别写死端口。** `config.py` 的 `PORT` / `HOST` 已支持环境变量（见「配置说明」），
   所以启动命令用 `python main.py` 就行。
   **不要**写成 `uvicorn main:app --port $PORT`——部分发布环境不经 shell 执行，
   `$PORT` 不会被展开，会报 `Option '--port' requires an argument`。

### 重新发布后「页面还是旧的」怎么办

托管环境前面有一层**边缘网关缓存**。默认情况下源站不给 `Cache-Control`，网关就按自己的
默认 TTL 缓存裸路径 `/`——于是出现一种很能误导演示的状态：

| 请求 | 缓存行为 | 结果 |
|------|----------|------|
| `/static/app.js`、`/static/style.css` | 带 `ETag`，网关走 `RefreshHit` **回源校验** | ✅ 新的 |
| `/`（入口 HTML） | 无 `Cache-Control`，网关长期缓存 | ❌ 还是旧的 |

现象就是"接口和脚本都更新了，页面上却看不到新功能"。**客户端无法强制回源**
（带 `Cache-Control: no-cache` 请求头、`Pragma: no-cache`、`max-age=0` 都无效，网关忽略），
只能等 TTL 到期。

**根治办法（已实现）**：入口 HTML 一律带 `Cache-Control: no-cache, must-revalidate`，
让网关每次回源校验（命中 304 几乎零成本）。见 `main.py` 的 `_NO_CACHE`。
这样以后重新发布即时生效。

**应急办法**：给链接加一个查询参数换掉缓存键，例如 `https://<你的域名>/?v=2`，
这条 URL 是全新的、必然回源，拿到的是最新页面。

> 排查这类"更新没生效"时，先看响应头里的 `Eo-Cache-Status` / `Age`：`HIT` + 较大的 `Age`
> 说明拿到的是缓存副本，不是你的新代码——别急着改代码。

### 方式二：局域网

把服务绑到 `0.0.0.0` 并放行防火墙端口，对方在同一网络下访问 `http://<你的内网IP>:18090`：

```bash
HOST=0.0.0.0 python main.py
```

### 线上与本地的差异（重要）

- **拍照识别会降级。** 在线沙箱通常自带 Tesseract 程序但**不带中文语言包 chi_sim**。
  此时引擎能力条会写明「已装 Tesseract 但缺少中文语言包 chi_sim」，拍照识别判定为不可用，
  引导走人工录入——不会静默失败，也不会误报成「照片模糊请重拍」。
  上传 PDF / DOCX 的完整审查链路不受影响。
- **数据存在进程内存。** 任务列表**和外发审核队列**都不落盘，服务重启即清空；多人同时访问看到的是同一份任务列表。
- **链接是公开的。** 拿到链接的人都能用演示账号登录，别放真实合同上去。
- **线上要真发钉钉，得注入环境变量。** `DINGTALK_WEBHOOK`（+ 加签时的 `DINGTALK_SECRET`）通过环境变量注入，
  不要在代码或界面里填生产机器人地址。**未配置时页面走模拟通道**，功能可完整演示但消息不会真发出。
- **权限是界面级的，不是安全边界。** 登录与角色权限都在前端（会话存 `localStorage`），
  后端接口**没有做鉴权**——这是本演示项目的既定取舍，不是疏漏。真要上线必须补服务端鉴权，
  否则任何人拿到链接就能直接调 `POST /api/export/{id}/approve` 往外发消息。

## 八、电商业务事件风控子系统

本子系统与合同审批审查系统**同属一个项目、同一个服务（端口 18090）、同一套前端框架**，
复用既有的 `config` 单例 / `NodeBase` 节点链 / FastAPI / 原生前端。它承接「电商业务事件风控」需求：
解析五类核心业务事件、实时计算行为频次与设备环境特征、按规则集完成风险评分与决策仲裁、
中高风险自动建案、用户画像与关联证据复核闭环、黑白名单维护、仿真回溯与态势大盘。

### 8.1 功能与验收标准对照

| 验收标准 | 落地位置 |
|---------|---------|
